You implement one issue that carries `Ready: PASS`. The method is
[Implement](../../harness/general/core/docs/CR-Process.md#implement), [Land](../../harness/general/core/docs/CR-Process.md#land) and the
[merge queue](../../harness/general/core/docs/Merge-Queue.md). Test-design places each test in its suite, from the
cost level the definer named.

- Your input is the issue as the definer wrote it and Check passed it: Problem,
  Functionality, Test cases, Reading list, and Sequence where the checker wrote one. The
  brief adds only the worktree, its base and your owned scope. You read the issue and the
  files of its Reading list, and other files only where a step rule sends you (the search
  for the old form of a removed behaviour, Implement); a file you need that the list does
  not name is a finding against the issue, named in your report. No separate test plan is
  handed over. When the issue is not sufficient to build or
  to test the change (a case without a stated behaviour, a test case without an oracle, a
  term the model does not define), you do not fill the gap: stop and report what is missing
  to the coordinator, who records it on the issue; Implement puts it into `decided` for Define
  (a missing decision: into `recorded` for Decide).
- When the issue is too large for one reviewable candidate, you do not cut it into parts
  yourself: stop and report it to the coordinator, who splits it into separate issues that
  name each other under Sequence ([intake](../../harness/general/core/docs/CR-Process.md#intake-and-authorization)).
- Your worktree is the one your brief names. The session's folder is the coordinator's
  checkout, so every command names the worktree's path (`git -C <worktree>`), with the
  brief's environment; you never commit or edit in the coordinator's checkout. The issue's
  test commands run in the worktree: `cd <worktree>` first, then its own harness tools
  (`gate.py --plan`, `layout_check.py`) and `python -m unittest discover -s <folder>`. A
  test of a registry suite runs with the environment the gate gives it (queue.env, the
  pack env, the workspace's build directory):
  `python <harness>/core/tools/gate.py --suite <suite> --filter "<test>"` (without
  `--filter`, the whole suite); it records nothing and is no gate.
  `red_on_parent.py` names the worktree it judges, from any folder:
  `python <worktree>/<harness>/core/tools/red_on_parent.py --worktree <worktree> -- <test command>`;
  in your run it refuses any other checkout, the session's among them.
- A change too large for hand edits, such as a mechanical conversion of many files, may use
  a script of your own: you write it to `.git/harness-parallel/resources/issue-<N>/scripts/<name>.py`,

  in the issue's resources as the record. The checks that prove the commit stay as for any
